Three phases, three different questions

01

Preparation

Did the robot enter the task already leaning? Compare task-onset orientation with the earlier standing capture. A large stationary initial offset is not the same as a disturbance generated by the trajectory.

02

Movement

Does realized counter motion reduce the additional base response? Compare requested, locally buffered and measured motion. A lower optimization residual alone does not establish better stabilization.

03

Recovery

Does the fade or posture return create a second disturbance? Retain full-record and terminal metrics alongside motion-only results. Do not select a transient win that leaves a worse endpoint.

Evidence and controlled checks

Historical hardware / supplementary phase diagnostics

There is no single “overhang balance problem.” Preparation sets a nonzero orientation offset, movement introduces additional rotation and tracking lag, and the fade/return phase changes the error vector again. The corrected 40-pair ledger is preserved; this decomposition adds explanatory diagnostics without changing its metrics.

Counter's overhang task-onset orientation RMS rises about 18.8%, while directional task-onset RMS falls from 0.468 to 0.388 deg. Gravity-direction displacement also increases on overhang (0.1815 → 0.2095 deg), so this is not purely a yaw effect. Mean overhang starting drift is already 1.239 deg for Frame and 1.168 deg for Counter.

Reference clarification: standing R₀ is captured at READY after automatic HOME, whose 14 arm targets are zero, and before PREPARE reaches the saved start. Task onset is the first observed execution state after PREPARE and START, not an exact zero-time sample. Both are measured pelvis orientations reconstructed from torso IMU plus joint FK; HOME arm targets are not an all-zero measured robot. See the reference timeline in iteration 7.

A clean tracking diagnostic: change time, not geometry

Offline reference-only experiment

Sampling the same saved spline at duration factors 0.8 and 1.2 preserves joint and Cartesian geometry to numerical precision. It reduces requested velocity to two-thirds and acceleration to four-ninths. This tests dynamic tracking sensitivity without choosing a different path or a more favorable metric.

Not a live command yet: the current CLI supports duration factors 0.8, 0.6, 0.5, 0.4 and 0.3 only. Choosing 0.6 makes motion faster. A slower factor needs a separately reviewed CLI extension and safety validation; no such extension or hardware run was performed here.
