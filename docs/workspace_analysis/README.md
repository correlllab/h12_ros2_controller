# H12 Gripper Workspace Analysis

Where each Magpie gripper can work for fixed gripper orientations, and how much of that
space the head camera sees.

- Open `h12_workspace_analysis.html` for the interactive report (self-contained, works offline).
- Positions are the grasp frame (fingertip point) in the pelvis frame, with the torso at 0.
- RPY is in degrees, using the same convention as `FrameController.set_frame_task_pose`.

- Every box point is reachable and inside the head camera color view.

  near-singular.
- Boxes keep z ≥ −0.05 and have no other x/y limits.

## Files

- `h12_workspace_analysis.html`: interactive report with all poses and the head camera cone.
- `h12_{left,right}_pitch{90,60,45}_robot.png`: robot, working box and head camera cone.
- `h12_{left,right}_pitch90_views.png`: top, side and front views of the pitch 90 box.
- `head_camera.json`: head camera pose, intrinsics and per-box camera coverage.
- `scripts/`: the analysis code (see below).
- `data/`: sweep results, regenerated by the scripts and ignored by git.

## Policy fine-tuning targets

Open `h12_workspace_targets.html` for an offline interactive plot of all 200 targets,
with wide 3D views of the targets, robot mesh and calibrated head-camera cone,
plus exact poses and training integration notes. The axes use equal meter scales.
The robot is shown at zero posture as a spatial reference.
The four self-contained catalogs are in `arm_targets/`:

- `arm_pitch_90_targets.yaml`: pointing down, 25 targets per arm.
- `arm_pitch_60_targets.yaml`: pitch 60°, 25 targets per arm.
- `arm_pitch_45_targets.yaml`: pitch 45°, 25 targets per arm.
- `arm_horizontal_targets.yaml`: horizontal forward, 25 targets per arm.

Each arm samples its own published working box using eight nearest feasible corners, six nearest
grid face centers, the nearest grid center and ten normalized farthest-point samples.
This samples the box boundaries and interior on the original 25 mm grid. It does not
attempt to cover the irregular reachable cloud outside these camera-visible boxes.
Left targets use `left_grasp_frame`; right targets use `right_grasp_frame`.
Preserve the full RPY, including the arm-specific roll and yaw, at zero torso.

The catalogs follow the mjlab schema-v1 `candidates` format and include explicit
pelvis-relative poses, 14-joint IK witnesses, joint order, static endpoint checks and
provenance hashes. Every selected solution is rechecked against the current models
when generated. The inactive arm and all other joints are held at zero.

The controller permits inward shoulder roll to −0.38 rad on the left and +0.38 rad
on the right, while the URDF limits it to −0.19 and +0.19 rad. Selection filters
source witnesses to the intersection of both limits with 0.05 rad clearance.
Some horizontal corner anchors consequently move to the nearest compatible grid
point; their labels describe the intended anchor. Catalogs record the effective
limits, compatible grid counts and coverage radius over the compatible source grid.

Copy the four YAMLs to `h12_mjlab/data/arm_targets/` and use a training task controlling
all seven joints per active arm with a grasp-frame pose objective. The current mjlab
ALMI manipulation parser keeps only four proximal joints; loading these catalogs
alone does not enforce their wrist orientations. Transitions, simultaneous arm pairs
and dynamics need validation in the training environment.

Regenerate the catalogs and HTML from the existing sweep data:

```bash
uv run python docs/workspace_analysis/scripts/training_targets.py
```

## Scripts

- `config.py`: paths, joint limits, camera calibration and pose definitions.
- `kinematics.py`: single-arm model, IK and solution quality.
- `sweep.py`: grid sweep with region growing, gap filling and right-arm mirroring.
- `analysis.py`: grid helpers, balanced box search and camera projection.
- `robot_mesh.py`: posed robot meshes from the URDF.
- `report.py`: interactive HTML report and `head_camera.json`.
- `figures.py`: static PNG figures.
- `run_all.py`: runs everything.

The scripts only depend on the repo environment (`pinocchio`, `scipy`, `plotly`,
`matplotlib`) and the URDFs in `submodules/CL_Assets/ros_assets`. The head camera
calibration is copied from GOLEM `h1_robocasa/realsense_profile.yaml` into `config.py`.

Run from the repo root:

```bash
# full analysis: sweeps, explanation tables, report and figures (about 1.5 h with 12 workers)
uv run python docs/workspace_analysis/scripts/run_all.py --workers 12

# skip the yaw/roll sweeps behind the explanation tables
uv run python docs/workspace_analysis/scripts/run_all.py --skip-tables

# rebuild the report and figures from existing data (under a minute)
uv run python docs/workspace_analysis/scripts/run_all.py --report-only

# sweep a single pose
uv run python docs/workspace_analysis/scripts/sweep.py --pose pitch60
```

- Keep `--workers` below the CPU core count; each worker uses about 250 MB.
- Sweeps that already exist in `data/` are skipped, so interrupted runs resume.
- Set `WS_DATA_DIR` to store sweep data elsewhere.

## Changing the analysis

- Add or edit a pose in `config.POSES`.
- The `box` entry pins the published boxes. Set it to `None` to search the box again:
  the most balanced box that is fully reachable, inside the camera view, and above the
  floor.
- Joint limits (`CLIP`), the clearance threshold (`MARGIN`), the grid (`GRID`, `STEP`)
  and the floor (`Z_FLOOR`) are all in `config.py`.
- A fresh sweep can differ slightly from the shipped data because the IK search is
  seeded; the pinned boxes were verified 100% reachable on the data used for the report.
